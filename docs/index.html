Which pages should an editor refresh first? A transparent rule vs. learned models

Muhammad Ramzan · FlyRank ML Internship · Lane: Refresh / Content Opportunity Scoring · November 2026

Abstract

We ask which content pages an editor should review first for a refresh. We rank 18,010 pages from 30 anonymized client sites by their risk of a demand drop (impressions in the latest 30 days more than 20% below the 30 days before), using only earlier-window and static page signals. A three-signal hand-written rule (young page, weak earlier CTR, real earlier demand) is compared with Logistic Regression and Random Forest on client-held-out folds. The rule reaches precision@50 ≈ 0.81 against a base rate ≈ 0.63, and the learned models do not beat it at the top of the queue. We keep the transparent rule as a decision-support queue and report where it is weak.

1. Introduction

A client site has hundreds of pages and an editor can review only a few each week. The decision this work supports is the order of that review queue. A wrong call either wastes an editor's hour (false alarm) or leaves a page with real demand sliding (miss).

Case study: the content problem

FlyRank publishes and refreshes content for many client sites; editors can review only a few pages a week. This work turns that into a per-client review queue with one reason code and one action per page, measured on sites the method never saw. It ships as decision-support, not automation.

2. Data

Public starter release content_refresh_anonymized.csv: 30,000 pseudonymized pages, 32 clients, one trailing-90-day snapshot. Inputs come from days 31–60 back plus static properties; the outcome comes from days 1–30 back. We exclude pages with fewer than 100 earlier-window impressions (noise), every last-30-day and trend column, 90-day totals/averages (they overlap the outcome window), days_since_last_update (≈60% of pages were updated inside the outcome window), tiers and product flags. No client names, URLs or queries are used.

3. Methodology

  • Label: demand_drop = latest-30-day impressions < 0.8 × previous-30-day impressions (base rate 0.62).
  • Features (19): earlier-window impressions, clicks, sessions and CTR; content age; keyword volume, competition, CPC; word count; missingness flags; content type; intent.
  • Baseline rule: score = 0.4·youth + 0.4·weak CTR + 0.2·demand (percentile ranks, nothing fitted), with one reason code and action label per page.
  • Models: Logistic Regression; Random Forest (300 trees, min leaf 20).
  • Validation: GroupKFold(5) by client — every score is measured on sites the model never saw. A random split inflates Random Forest AUC from ≈0.60 to ≈0.70, which is memorized client character.
  • Leakage checks: forbidden-column assertion; a deliberately leaky last-30-day score reaches precision@50 = 1.00, showing what leakage looks like.

5. Limitations & honest framing

  • Findings are observed and directional, for decision support only; no causal claim that a refresh recovers traffic, and nothing about how Google ranks pages.
  • One snapshot: no calendar-time test; a 30-day change can be seasonal.
  • For pages older than a year the ranking is weak (rule AUC ≈ 0.54).
  • Client-level events move all pages together and are invisible here; two large clients are half the data.

6. Ranked recommendations (action playbook)

  1. ZERO_CLICK_YOUNG_PAGE → rewrite title and meta.
  2. WEAK_CTR_WITH_DEMAND (CTR < 0.5% on ≥ 1,000 impressions) → refresh snippet and intro.
  3. YOUNG_PAGE_SETTLING → light refresh, then monitor 30 days.
  4. LOW_RISK → monitor only.

Use per-client queues (top-5 per client: observed drop rate 0.69 vs 0.62 base) and skip pages whose keyword volume is ~0.
